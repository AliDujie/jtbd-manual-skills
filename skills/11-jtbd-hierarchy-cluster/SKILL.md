# L1/L2 分层聚类

## 触发场景

- 35 列场景库已完成，准备做分析、写报告
- 100 条以上、甚至上千条场景需要归并成可决策的 L1/L2
- 已经分好，但“其他”占比过高、单用户 L2 过多，或名字虚得没法动手
- 需要把分层表用于报告组织、评审汇报或交给 PM 认领

## 这一步产出什么、往哪儿接

- **输入**：35 列场景库，每行一条场景
- **产出**：L1/L2 分层表、每个 L2 的场景清单、合并映射表、健康度校验报告
- **报告怎么用**：L1 归大块，L2 归具体分析；一章里放几个 L1、一个 L1 拆成几节，按报告篇幅来定，不必一个 L1 铺成一章。每个 L2 的场景数、覆盖用户数、四力（推力、拉力、焦虑、惯性）均值、引用哪几句原话，都从这一层汇总。报告里“几个人提到”“这个方向强不强”这类说法，先有这层归组，才数得清、比得了。
- **下游**：jtbd-forces-analysis（关卡 8）按 L2 做四力打分和优先级排序

## 核心能力

### 能力一：分层四原则

1. **名字要具象**：L2 是 PM 看到就能写 PRD 的方向，不是口号。三组反例：
   - “退订体验优化” → “订单页一键退订功能建设”
   - “用户信任建设” → “实拍图集聚合与展示”
   - “信息透明度提升” → “默认勾选与隐形添加机制整改”
2. **粒度对齐业务动作**：按“谁来解决、怎么解决”切，不按学术框架切。“功能性、情感性、社会性”看着完备，可“信任缺失”归进情感性，解决它要靠评价系统、认证标识、担保交易——三个团队、三个迭代的事，绑在一个主题下，PM 拆不开。
3. **层数对着场景总量走**：
   - 100 到 300 条：6 到 8 个 L1，每个下辖 2 到 3 个 L2
   - 300 到 700 条：8 到 10 个 L1，每个 3 到 4 个 L2
   - 700 条以上：8 到 12 个 L1，每个 3 到 5 个 L2
   - L1 封在 12 个以内。PM 一次能同时关注的业务领域，十个上下就到顶
4. **一条不落**：每条场景都得有归处。大量场景只能塞进“其他”，就是分层设计漏了东西的信号

### 能力二：三健康度硬指标

分层定稿前，三个数字同时过一遍。任何一个不过，先别定稿。

- **“其他”占比 ≤ 2%**：把“其他”里的场景重读一遍，找共性。看出新主题，就拆一个 L2；只是零散，就逐条归进最像的 L2；怎么都归不进，回查清洗时漏掉的非主题场景
- **平均场景每 L2 ≥ 3 条**：不到 3 条的 L2，并进同一个 L1 里主题最近的邻居
- **单用户 L2 ≤ 30%**：只有 1 位用户覆盖的 L2，超过总数三成，整张表的可信度会被“这就一个人说的？”问住。处理办法同上，并进同 L1 的相近主题，合完重新数

三个数字要同时站住。只盯着消灭“其他”，把零散场景随手塞进最像的 L2，“其他”降下去了，单用户 L2 会跟着飙上来。

### 能力三：名字过两道闸

**第一道闸，禁词。** 命中直接打回：

- 其他、其它、杂项
- 一般、常规、通用
- 相关、有关
- 未分类、待定
- “XX 路径”“XX 方式”这类说了等于没说的写法

禁的理由只有一条：说不具体。“退订路径优化”，先问是哪条路径，写清楚，“订单页一键退订”或者“客服工单退订”。名字里带着“一般”“常规”，把“具体是什么”追出来；追不出来，说明这个 L2 还没分到位。

**第二道闸，30 秒测试。** 把名字念给一个没参与项目的 PM 听：

- 他立刻说出“哦这个是要做××” → 过
- 他反问“这个具体是指什么” → 名字太抽象，回炉
- 他说“这个太大了，得拆几个” → 粒度太粗，回炉

自己念给自己听，多半挑不出毛病——你知道名字底下压着什么，业务方不知道。公司里找不到合适的 PM，拉一个完全不了解这个项目的同事也成，反应骗不了人。

### 能力四：合并连带五件事

分层过程里，合并是常态。最容易出的错不在名字上，在名字背后的数字。每合并一次，五件事跟着走一遍：

1. **场景总数核对**：新 L2 的场景数加起来，等于合并前的总数，一条不多一条不少
2. **四力重算**：新 L2 基于合并后的场景集合，重新算推力、拉力、焦虑、惯性
3. **全文引用替换**：旧名字在报告各处的引用批量换新，一处不留
4. **统计图表重算**：涉及 L2 的所有统计和图表，重跑一遍
5. **报告开头概况更新**：报告开头那句“多少 L1 × 多少 L2”，改成合并后的数字

### 能力五：合并映射表

输出 `{project}_l2_merge_map.json`，每个被合并的 L2 记四项：

- 原名
- 去了哪里
- 为什么合
- 合之前多少场景、多少用户

平日用不上。等到你或别人接手重跑，它能复原当时的判断；业务方追问“怎么把 A 并进 B 的”，翻出这张表就能讲清。

### 能力六：人工先做一遍，AI 出初稿

分层这件事，机器做起来快，但头一遍最好人工做一遍。挑一百来条场景，把四原则、三个健康度、两道闸都走一遍。分层看着是搭结构，真功夫全在对场景的熟悉：哪两条看着像，其实归不到一组，哪个名字底下压着两个业务动作，哪一组合并完数字会掉下来，切过一遍心里才有底。

没切过，机器交回来的结构，你只能拿清单逐条核对；它把两个团队的方向并进一个 L2，你也看不出问题。自己做过一遍，写 prompt 时才知道哪些口径必须交代清楚；机器交了稿，也知道先翻哪几处。判断机器、给机器立规矩，靠的都是手上这点经验。

练完这一遍，再让机器出初版，四个子任务都能先出一版：

- **初步分层**：基于场景库生成 L1/L2 候选结构和每条场景的归属
- **命名建议**：每个 L2 出 3 到 5 个候选名
- **健康度扫描**：三个指标自动数一遍
- **连带审计**：合并后的五件事自动跑

一个可用的 prompt：

> 这是一份 35 列的场景库表，每行一条场景。
> {粘贴场景库}
> 按业务动作分层，层数按场景总量定（100 到 300 条：6 到 8 个 L1，每个 2 到 3 个 L2；300 到 700 条：8 到 10 个 L1，每个 3 到 4 个 L2；700 条以上：8 到 12 个 L1，每个 3 到 5 个 L2），命名具体到能直接立项。
> 所有 L1、L2 的名字不得出现其他、杂项、一般、常规、通用、相关、未分类、待定这些词，也不许用“XX 路径”“XX 方式”这类说了等于没说的写法。
> 每条场景必须归入某个 L2，一条都不许未归类。
> 输出 L1/L2 结构表，每个 L2 下列出用户ID+场景序号，末尾附健康度统计，包括其他占比、平均场景数、单用户 L2 占比。

机器出稿之后，人的活集中在审：候选结构过四原则，候选名挑最贴业务的，指标不过的定下来是合并还是重分，审计报错的一项项处理。尤其“这个 L2 能不能直接立项”这一问，机器答不了，它没见过你们 PM 的排期表。

## 输出形态

- 分层后的 L1×L2 结构表
- 每个 L2 的场景清单（用户 ID + 场景摘要）
- L2 合并映射表 JSON
- 三健康度校验报告

## 常见踩坑（本 skill 内置校验）

- **把指标当靶子打**：三个健康度是信号，不是考试分数。“其他”偏高，不去重读场景，直接把零散条目塞进最像的 L2，占比压下去了，塞进去的东西没想清楚，下一个环节照样卡壳。先读完，再动手
- **改名不重算**：改完名直接交付，到了汇报现场，同一个 L2 在两张图里场景数对不上。五件事不做，省下的功夫全在汇报现场还回去
- **学术框架回潮**：分着分着拐回“功能性、情感性、社会性”，因为那样看起来整齐。整齐归整齐，到了排期，一个认领的团队都找不到。切回“谁来解决、怎么解决”
- **自检做给自己看**：30 秒测试在工位上默念，“我知道下面是什么，没问题”，这种自检等于没检。测的人是你自己，算不算过，得问没读过场景库的人
- **名字虚或拆得碎**：名字虚得没法动手，拆得碎得看不出重点，都过不了 PM 的 30 秒测试
