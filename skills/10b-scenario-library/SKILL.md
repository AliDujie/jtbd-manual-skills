# 场景库分析

> 本Skill处理"场景库"类型的用研数据（Excel），覆盖数据解析→场景合并→四力分析→深度HTML报告生成的完整流程。理论框架与展现方法论由随包 jtbd_essentials.md / swd_essentials.md 承接。

## 一、触发条件与协同加载

**触发**：上传场景库Excel / 要求JTBD分析 / 要求生成场景分析报告 / 提到"场景合并/分层/整理"。手上是 Markdown 表时，先另存为 xlsx，表头保持 35 列顺序，不要先改列名。

**随包理论字典**：激活后读取本Skill同目录下随包发布的 `jtbd_essentials.md`（四力模型、九大原则、竞争三分类、创新信号类型与增强因子、Big/Little Hire、颠覆三分法、Demand Thinking、OST）/ `swd_essentials.md`（图表选择决策树、注意力引导、三幕叙事、设计评估三维度）两个后备理论字典，两个文件必须随Skill一同分发。

**理论字典内容**：`jtbd_essentials.md`（四力定义+净推动力公式+九大原则+竞争三分类+创新信号类型与增强因子+机会评分+Job Map+Wunker七维度+分析参考框架）/ `swd_essentials.md`（六课方法论+图表选择决策树+注意力引导+设计评估+五维度诊断）是本Skill运行时的查找数据，**必须随Skill一同分发**，缺失则理论降级（按表内字段定义工作）。

**展现方法论的应用方式**：swd_essentials.md 的方法论用于指导报告设计。生成HTML报告时，Agent应将展现建议**内化为设计决策**（选择图表类型、颜色策略、叙事结构），而非将方法论文本直接嵌入HTML。

## 三、深度标准

### 3.1 洞察的输出标准

每个分析模块的洞察必须包含**判断**，视情况包含预警和行动建议：

- **🔍 判断**（必须有，insight-judge蓝色）：立场鲜明的结论句。"XX是当前最大的问题"而非"用户对XX有一些不满"
- **共情叙事**（现象值得讲时用）：用一个典型用户的故事让读者感同身受
- **⚠️ 预警**（有风险时写，insight-warn黄色）："如果继续忽略XX，将面临XX风险"
- **✅ 行动建议**（有方向时写，insight-advise绿色）："建议XX，代价是XX"

判断是底线——没有判断的分析是废话。预警和行动有就写、没有不硬凑。

**每条洞察的内部结构——"总-分-总"**：
1. **总（结论）**：第一句话直接给出判断结论，不要从数据描述开始
2. **分（佐证）**：用1-2个最典型场景佐证，必须包含用户原话
3. **总（决策含义）**：回到这个发现对产品决策意味着什么

### 3.2 深度的检验标准

- **"So What"测试**：对任何发现连问三次"所以呢？"——如果第三次还是循环性结论，分析不够深
- **反直觉发现**：模块一必须包含至少一个"跟直觉不一样"的发现
- **矛盾不回避**：好报告解释矛盾为什么共存，而不是假装不存在
- **行动带代价**：只有收益没有代价的建议，决策者不会信任
- **5层洞察链**：数据→现象→原因→影响→行动。只到"现象"层的分析是半成品

### 3.3 禁止的写法

- ❌ 纯数据罗列（"75个场景中55个净推动力为正"——然后呢？）
- ❌ 正确的废话（"用户体验有待改善"——谁不知道？）
- ❌ 无佐证的判断（"这是最大的痛点"——证据呢？）
- ❌ 无观点的综述（平铺直叙列事实，读完不知道该做什么）
- ❌ 学术化推演（"P=2.54,L=3.30,所以(P+L)/2=2.92..."——读者不需要验算公式）

### 3.4 正确的写法示例

> "用户的核心矛盾不是'酒店贵'——而是'不确定花的钱值不值'。（判断）用户H说'升房如果能确定，贵两百我也愿意'——付费意愿已在，缺的是确定性。（佐证）如果平台继续把'升房'当不可控的惊喜而非可承诺的服务，高端用户会绕过平台直接联系酒店——事实上已有3位用户在这样做。（预警）建议构建'升房确定性引擎'：预订时显示升房概率，入住前24h推送结果。代价：需要酒店侧数据接入，短期增加BD成本。（行动+代价）"

### 3.5 模块一专属深度规则

模块一是整篇报告的"门面"和"结晶"——不是各模块结论的摘要，而是全报告最有价值的一页。

**规则1（Y1）：h3标题必须是判断句**
格式：`板块名：结论性判断句`
- ✅ "全局判断：90%的痛苦发生在'订票'之外——用户要的不是比价器，而是全流程管家"
- ❌ "全局判断"（纯结构标题）

**规则2（Y2）：矛盾与破局"问题→解法"配对结构**
每个矛盾和对应解法紧挨在一起，禁止先列完矛盾再列解法。

**规则3：矛盾描述要具象**
PM读标题就懂，不要抽象。
- ❌ "确定性饥渴 vs. 平台的无能为力"
- ✅ "用户想在下单时就知道能不能升房，但飞猪作为第三方平台给不了这个答案"

**规则4：全局判断两段式**
第一段：核心结论（判断句开篇）。第二段：数据佐证。

## 四、执行流程

### 执行总纲

```
阶段1: 数据解析 → 阶段2: 场景合并 → 阶段3: 四力分析
    ↓
阶段4: 全局分析想透（先想） → 分Part生成HTML+cat合并（后写）
    ↓
阶段5: 4层自检 → 交付
```

**关键决策点（5个判断）**：
1. 字段映射数≥30？（含8个ODI字段）→ 否则阶段1失败
2. 用户按完整用户ID去重，ID里的场次后缀已按上游口径显式映射？→ 否则用户数失真
3. ODI字段非空率≥30%？→ 是则必须做ODI富化分析
4. 用户提供了研究目标？→ 是则必须9模块
5. 4层自检全部0问题？→ 否则禁止交付


### 阶段1：数据解析

> **🔴 本阶段检查清单**：
> 1. 字段映射数≥30（含8个ODI字段）
> 2. 用户ID按上游定义去重；带场次后缀的先显式映射（R4）
> 3. 研究对象边界确认（Y8）
> 4. 数据清洗+基础统计输出
> 5. 字段脏值清洗（Y17）

**目标**：将Excel文件转化为结构化JSON，输出基础统计概览。

**操作步骤**：

1. **读取Excel**：用openpyxl读取，逐行扫描找到含"用户ID""推力P"等关键字的行作为表头（不要信任max_row，必须检查每行是否有实际数据）

2. **字段标准化映射**（≥30个字段）：

| 常见中文列名 | 英文字段名 | 类型 |
|---|---|---|
| 用户ID / 受访者 | user_id | string |
| 分类 / 原始分类 | cat | string |
| 阶段 / 进步阶段 | stage | string |
| 场景 / 场景描述 | scene | string |
| 进步 / 期望进步 | progress | string |
| 现状 / 当前方案 | current | string |
| 是否补偿行为 | has_compensation | string（是/否） |
| 补偿行为描述 / 补偿行为 / 替代 | compensate | string |
| 推力P / Push | P | float |
| 拉力L / Pull | L | float |
| 焦虑A / Anxiety | A | float |
| 惯性I / Inertia | I | float |
| 用户原话 / 引用 | quote | string |
| 改进建议 | improvement | string |
| 评分 / 总分 | score | float |
| Outcome Statement / OS | outcome_statement | string |
| Job Map阶段 | job_map_stage | string |
| Job维度 | job_dimension | string |
| 创新信号强度 | innovation_signal | float |
| 创新信号类型 | innovation_signal_type | string |
| 竞争关系 | competition_type | string |
| 付费意愿信号 | willingness_to_pay | string |
| 频次信号 | frequency | string |

> ⚠️ Agent容易只映射前24个基础字段而漏掉后8个ODI字段（尤其是「创新信号类型」「竞争关系」两个清洁标签列）。映射完成后必须打印"映射字段数: N"，N必须≥30。
> **R23（关键对齐）**：上游场景库为35列时，「创新信号类型」「竞争关系」是上游专为本报告聚合而预先标注的清洁标签列——**模块六的竞争三分类占比、模块七的创新信号类型占比必须直接读这两列，禁止再从 current/compensate 文本重新判断**（文本重判口径不一致，正是上游补这两列要消灭的问题）。若上游为旧33列（无这两列），则降级回文本推断并在报告脚注标注口径。

> **补偿字段先分清两列**：35列的「是否补偿行为」是是/否标记，「补偿行为描述」才是动作文本。若上游只有一列“补偿行为”，先看值是“是/否”还是动作描述，分别映射到 `has_compensation` 和 `compensate`；不要把“是”当描述，也不要把描述当标记。

3. **数值字段转float；空值保留None，不填0**。均值、占比计算时剔除None，并在报告中注明有效分母；只有“场景条数”这类明确计数的字段才以0起算。

4. **用户ID去重（R4，关键步骤）**：
   - 以上游定义的完整 `user_id` 为准去重，不默认截掉下划线后的部分
   - 若上游把访谈场次写进ID（如 `Name_01`、`Name_02` 是同一人的两场），先向上游确认ID规范，建立显式映射表再计数；映射表随报告留档
   - 没有映射依据时，宁可把两个ID当两个用户并在报告注明，不静默合并
   - 验证：深访数据中每人通常贡献几十条场景，如出现“用户数≈场景数”，先查ID规范，不要直接截尾
   - 输出：原始ID数、去重后独立用户数、每人场景数、ID映射表（如有）
   - 多数据源合并：跨文件合并后按同一映射表再次全局去重

> 来源：曾把`WuHuiYing_01`、`WuHuiYing_02`当成两个不同用户，导致一份6人深访的报告显示“485位用户”，所有“N位用户共识”的论据强度全部虚高。反向的错也发生过：一律截掉下划线后缀，把两个真实用户合成一个。去重的前提是知道ID规范，先确认后缀含义，再决定映射；没有依据就分开计数并注明。

5. **研究对象边界确认（Y8）**：
   当研究对象名称容易与其他产品混淆时（如"飞猪千问"vs"通义千问"），必须在分析前向用户确认精确范围。混入场景不要简单剔除——标记`is_reference=True`作为同源参照纳入竞争分析。报告正文严格使用全称，简称仅在quote区块中保留。

6. **数据清洗**：
   - 逐条扫描scene和quote字段，识别与研究主题无关的内容
   - 展示清洗清单（场景编号+内容摘要+剔除理由），确认后执行
   - 保留边界案例（核心语义相关的保留）
   - 输出：原始N条，清洗后M条（剔除K条非主题场景）

7. **字段脏值清洗（Y17）**：

| 字段 | 脏值识别 | 处理 |
|------|---------|------|
| outcome_statement | 命中Job Map阶段词(Execute/Monitor等)或Job维度词(Core Functional等)=确定性脏值；长度<20字符只标"待审"（真OS可以很短，筛子不是标准） | 确定性脏值：视为缺失，统计时排除；待审项：人判"像不像一整句话"，不像才当缺失 |
| job_map_stage | 不在标准8阶段内 | 标记"未识别" |

> **🔴 本阶段检查清单**：

**必算指标**（每个L2）：

- compensate_count, compensate_rate（分子只计已确认“是且有动作”的场景；分母为已定案场景〔确认是+确认否〕，待复核与缺失单列、不进分母）

- users（去重后）, stages分布

**补偿判断逻辑（R18）**：
```python
# 只放具体动作线索；不放“用/找/问”这类单字，避免“不用，没遇到”被误判
ACTION_CUES = ('自己', '打电话', '搭', '替代', '凑合', '拼单', '绕过',
               '改用', '换用', '截图', '比价', '手算', '表格', '备忘录',
               '记下', '记录', '整理', '提前问', '多问', '托人', '找人', '找朋友')
DENIAL_CUES = ('不用', '没做', '没有专门', '没专门', '不需要', '没遇到',
               '没试', '没弄', '没折腾', '没有')

def looks_like_action(s):
    return any(k in s for k in ACTION_CUES)

def denial_only(s):
    return any(k in s for k in DENIAL_CUES) and not looks_like_action(s)

def compensation_status(d):
    flag = str(d.get('has_compensation', '')).strip()
    desc = str(d.get('compensate', '')).strip()
    empty = ('', '无', 'None', '/', '-')
    if flag == '是':
        return 'yes' if desc not in empty and looks_like_action(desc) else 'review'
    if flag == '否':
        if desc in empty:
            return 'no'
        if looks_like_action(desc):
            return 'review'
        return 'no' if denial_only(desc) else 'review'
    if desc in empty:
        return 'missing'
    return 'yes' if looks_like_action(desc) else 'review'
```

自检：跑完后打印`补偿率=N/M=X%`（M=已定案场景数），同时打印“待复核”和“缺失”条数；100%或0%都要复查。待复核项必须人工回原文定，确认后才进补偿率，确认前单列。

> 来源：曾出现补偿率算成100%的事故——根因是把“否，我一般直接打电话”这类带否定的句子直接计入补偿，或把“是”当成有动作。另一个反向错误是把“没有专门做什么，就是会直接打电话问”这类描述了动作的句子，按“否/不”开头一刀切掉。判断只能看有没有具体动作：只否认、没有动作的不算；有动作但前面带否定的，标“待复核”；“是”但没描述的，也标“待复核”。虚高到100%会让“补偿行为=创新机会”的整章结论全盘失真。

**ODI衍生指标（R2，数据含ODI字段时必算）**：
- job_map_distribution：8阶段场景分布→识别卡点集中阶段
- job_dimension_distribution：7维度分布→功能驱动vs情感驱动
- innovation_signal_mean：>3.5为高创新机会主题
- innovation_type_distribution（R23）：按「创新信号类型」列统计 补偿行为/非消费/不满意使用/异常使用/情境变化 各自占比与代表场景→供模块七创新信号类型占比板块直接透视，不从文本重判
- competition_distribution（R23）：按「竞争关系」列统计 直接/间接/不用方案 各自占比与代表场景→供模块六竞争三分类直接透视，不从文本重判
- wtp_rate：>20%为高商业化潜力主题
- frequency_distribution："日/周"占比高=高频痛点
- innovation_grade（Y19，每个L2主题做创新信号S/A/B/C分级，框架来自 jtbd_essentials.md 创新主线）：
  - **S级**：3+种创新信号类型叠加 + 大量非消费（创新信号类型=非消费占比>30%）+ 颠覆条件成立 → 新产品/新业务线
  - **A级**：2+种信号叠加 + 高频高痛（frequency=日/周占比高 且 痛点密集）→ 重大功能升级
  - **B级**：1种信号 + 创新信号强度≥3.5 → 体验优化
  - **C级**：有信号但样本量不足（覆盖用户<样本量有效门槛）→ 持续监测
- top_outcomes：去重TOP3 Outcome Statement
- job_map_emotion_curve（G9，数据含job_map_stage+情绪状态时）：按Job Map 8阶段聚合情绪状态（正/中/负计数或均值），得到一条跨阶段情感曲线→识别情绪谷底阶段，供模块四/七的体验旅程视角使用

**输出文件**：`{work_dir}/{project}_l2_analysis.json`

```python
    insight_l2_kw = ['画像','畅想','习惯','社群','AI辅助','偏好','认知','底料']
    if any(k in l1 for k in insight_l1): return False
    if any(k in l2 for k in insight_l2_kw): return False
    return True
```

**策略务实化原则**：
- 假设"团队只有30%资源可投入"
- 影响营收的建议标注"需权衡"
- 禁止"全面重构""打造生态"等大词
- 每条建议足够具体到PM能评估"几个人做几个迭代"

#### 布局一致性规则

- **所有section必须在container内**——结构必须是：
```html
<div class="container">
  <div class="section" id="m1">...</div>
  <div class="section" id="m2">...</div>
  <!-- 更多section -->
</div>
```
- **禁止HTML5 `<section>` 标签**：一律用`<div class="section">`。`<section>`在不同渲染环境默认样式不一致，且分Part拼接时易与container嵌套出错；若脚本产出了`<section id="modN">`，合并后必须脚本替换为`<div class="section" id="mN">`、`</section>`→`</div>`。
- Part拼接时检查container开闭标签跨Part情况
- **双Tab结构中的section处理**：精华版`<div class="content-summary">`内的各模块section**不再需要外层container包裹**（因为已在最外层`.container`内）。完整版`<div class="content-full">`同理。即Tab内的section是平铺的，不要再嵌套container。：每个Part首个section前确认是否已在container内（否则补开`<div class="container">`），最后一个Part末尾确保所有container正确关闭。
- **自检**：合并后检查每个`<div class="section"`之前是否有对应`<div class="container">`，section禁止裸露在container外。

### 诚实边界：为什么不引入 Ulwick 机会分数（Opportunity Score）

**结论：本Skill刻意不计算、也不要求上游补「重要度/满意度」数值列。这是经过权衡的决定，不是遗漏。** 后续维护者或其它 Agent 若想"补齐 Ulwick 机会算法让分析更全",请先读完本节再决定。

不引入的两条核心理由：

1. **数据性质不匹配（最根本）**。Ulwick 机会分数 = 重要度 + max(重要度−满意度, 0)，它的全部可信度建立在"重要度/满意度是结构化问卷量测、且样本量足够大"之上（Ulwick 原方法建议 N≥180 才稳定）。而本Skill的输入场景库来自**定性深访**（常 N=6 到几十），35 列是从访谈文本编码/推导出来的。若让上游场景库去补这两列，数值只能由 AI 从单条原话里"猜"——这是**伪精确**，即把没有量测支撑的分数包装成可排序指标，再拿去排 TOP、定优先级，会**误导**决策。这正是本Skill反复警惕的"编数据"反模式。

2. **与现有机制高度重叠、非正交**。报告的优先级判断已是多信号的：净推动力（四力）× 场景密度的**田字格四象限**、创新信号 **S/A/B/C 分级**、**频次高频高痛**、**付费意愿信号**。机会分数里的"重要度"≈ 痛点强度/净推动力，"满意度差距"≈ 补偿行为/不满意使用信号——它与已有的轴是**相关的、不是独立的**。再叠一条相关打分轴，不会让结论更清楚，只会让同一个 L2 在六七个分数之间"打架"，**加剧决策瘫痪**而非提升清晰度。这与本Skill把理论框架限定为"参考层、不进输出列"是同一条克制原则。

**唯一的未来触发条件**：当且仅当数据采集方式从"深访"切换为"量化问卷"（对每个 outcome 让足量用户实际打分重要度/满意度，样本量满足统计要求）时，机会分数才有真实量测基础。届时才走"上游场景库补两个**数值**列 → 本Skill 模块七新增机会分数排序板块"的路径，且应注明样本量与置信区间。在那之前，保持现状即正确做法。

### 10.7 多源加权合并（G7，阶段1多份场景库时用）

```python
# 合并多份场景库：主线权重1.0，辅助0.5；用户覆盖不加权
def merge_sources(sources, id_map=None):
    # sources = [{'name':'主线','weight':1.0,'rows':[...]}, {'name':'辅助','weight':0.5,'rows':[...]}]
    # id_map：可选的显式用户映射（如上游把访谈场次写进ID：{'Name_01':'Name','Name_02':'Name'}）
    all_rows, users_seen = [], set()
    for s in sources:
        for d in s['rows']:
            d['_weight'] = s['weight']
            d['_source'] = s['name']
            all_rows.append(d)
    # 跨源全局用户去重：按完整ID；有映射表先映射，不默认截尾
    for d in all_rows:
        uid = str(d['user_id']).strip()
        users_seen.add(id_map.get(uid, uid) if id_map else uid)
    raw_n = len(all_rows)
    weighted_n = sum(d['_weight'] for d in all_rows)
    user_n = len(users_seen)
    print(f"双口径: {raw_n}条原始 / {weighted_n:.0f}加权等效 / {user_n}位用户")
    return all_rows, raw_n, weighted_n, user_n

# 加权指标：场景密度/四力/付费意愿/补偿率用加权分母；用户覆盖数用去重计数
def weighted_metric(rows, value_key):
    vals = []
    for d in rows:
        v = d.get(value_key)
        if v is None or str(v).strip() in ('', 'None'):
            continue
        try:
            vals.append((float(v), d['_weight']))
        except (TypeError, ValueError):
            continue
    den = sum(w for _, w in vals)
    return sum(v * w for v, w in vals) / den if den else None
# 注意：缺失值不填0、不参与分母；返回 None 表示该指标不可算，报告注明有效分母。用户分型只基于主线数据（weight==1.0）
```

> 来源：把辅助调研（如小样本回访）和主线深访1:1混算，让一个小补充样本拉偏了整体四力均值。加权合并让辅助数据"参与但不喧宾夺主"，同时报告必须双口径披露原始/加权/用户三个数，避免读者误读样本量。

```python
import os
# ✅ 原子替换：os.rename 在同一文件系统下是原子操作，失败也不会丢原文件
def atomic_replace(new_tmp_path, final_path, archive_dir='archive'):
    if os.path.exists(final_path):
        os.makedirs(archive_dir, exist_ok=True)
        ts = __import__('time').strftime('%Y%m%d_%H%M%S')
        os.rename(final_path, os.path.join(archive_dir, f"{os.path.basename(final_path)}.{ts}.bak"))
    os.rename(new_tmp_path, final_path)   # 原子提交
# ❌ 禁止：os.remove(final) 然后 write(final)——中途异常会两头落空，报告丢失
```

### 10.14 交付前一键全检（编排脚本，阶段5最后一步必跑）

把上面 10.1–10.12 各维度的检查编排成一个脚本，对最终 `index.html` 跑全套硬规则，汇总 PASS/FAIL，**任一硬规则 FAIL 即退出码=1、禁止交付**。目的：避免"分散的脚本漏跑某一项"。软规则项只 WARN 供人工确认。

```python
# 用法: python3 check_all.py index.html
import re, sys

BRAND_WHITELIST = {'JTBD','ODI','PMF','TAM','SAM','SOM','CSS','HTML','PRD','AI','VIP','APP','OTA','SVG'}
META_FORBIDDEN = ['skill版本', '规则编号', '合规度', '健康度', '自检', '更新说明', '合并历史', '/14规则']

def load(path):
    with open(path, encoding='utf-8') as f:
        return f.read()

def check_structure(doc):
    fails = []
    if '<section' in doc:
        fails.append('出现 <section> 标签（应统一用 <div class="section">）')
    ci = doc.find('class="container"')
    if ci == -1:
        fails.append('缺少 .container 容器')
    else:
        for m in re.finditer(r'class="section', doc):
            if m.start() < ci:
                fails.append('存在未被 .container 包裹的 .section')
                break
    return fails

def check_blocks(doc):
    need = {'hero': 'class="hero"', '目录TOC': 'class="section toc"', 'Footer': 'class="report-footer"'}
    return [f'缺少 {name} 区块（{pat}）' for name, pat in need.items() if pat not in doc]

def check_tables(doc):
    fails = []
    for i, tbl in enumerate(re.findall(r'<table.*?</table>', doc, re.S)):
        rows = len(re.findall(r'<tr', tbl))
        if rows < 3:
            fails.append(f'第{i+1}个表格仅 {rows} 行（含表头需≥3，空表=返工）')
    return fails

def check_meta(doc):
    hits = [w for w in META_FORBIDDEN if w in doc]
    return [f'交付报告含技术元信息禁词: {hits}'] if hits else []

def check_css_sync(doc):
    style = ''.join(re.findall(r'<style.*?</style>', doc, re.S))
    core = ['insight-judge', 'quote', 'evidence', 'card-title', 'report-footer', 'quadrant-cell']
    miss = [c for c in core if ('class="' + c) in doc and ('.' + c) not in style]
    return [f'HTML用到但CSS未定义的class: {miss}'] if miss else []

def check_english(doc):
    body = re.sub(r'<style.*?</style>', ' ', doc, flags=re.S)
    body = re.sub(r'<[^>]+>', ' ', body)
    bad = sorted({w for w in re.findall(r'[A-Za-z]{4,}', body) if w.upper() not in BRAND_WHITELIST})
    return [f'疑似未中文化英文残留(抽样): {bad[:10]}'] if bad else []

def check_strong(doc):
    n = doc.count('<strong>')
    return [f'<strong> 计数 {n} 偏高（建议≤120，超130%必查）'] if n > 150 else []

HARD = [('结构骨架(container/section)', check_structure),
        ('关键区块(hero/toc/footer)', check_blocks),
        ('表格非空', check_tables),
        ('无技术元信息', check_meta),
        ('CSS class双侧同步', check_css_sync)]
WARN = [('中文化残留(抽样)', check_english),
        ('strong计数', check_strong)]

def main():
    if len(sys.argv) < 2:
        print('用法: python3 check_all.py index.html'); sys.exit(2)
    doc = load(sys.argv[1])
    hard_fail = 0
    print('== 硬规则(FAIL=返工) ==')
    for name, fn in HARD:
        issues = fn(doc)
        if issues:
            hard_fail += 1
            print(f'[FAIL] {name}')
            for it in issues:
                print(f'       - {it}')
        else:
            print(f'[PASS] {name}')
    print('== 软规则(WARN=人工确认) ==')
    for name, fn in WARN:
        issues = fn(doc)
        tag = 'WARN' if issues else 'PASS'
        print(f'[{tag}] {name}')
        for it in issues:
            print(f'       - {it}')
    verdict = '全部通过，可交付' if hard_fail == 0 else f'{hard_fail} 项硬规则未过，禁止交付'
    print(f'== 结论: {verdict} ==')
    sys.exit(0 if hard_fail == 0 else 1)

if __name__ == '__main__':
    main()
```

> 说明：本脚本是兜底总闸，不替代各维度脚本的细节排查；中文化/strong 列为 WARN 是因为品牌白名单需按项目补充（误报需人工判定），其余 5 项为硬 FAIL。退出码=1 时禁止交付。

## 十一、分析判断准则

### 用户原声补位与结论匹配

1. **人味儿优先**：口语保留，只做最小通顺化。判断标准：读出来像不像真人说话？
2. **语义精准匹配**：选原声佐证时必须检查实际语义是否支撑结论（挑房≠升房）
3. **概念边界严格**：不确定时保守归类，用用户原话表述

### 跨平台行为整体视角

1. 不把单平台行为等同用户全貌
2. 从场景集合还原完整行为链
3. 结论标注行为发生的平台上下文
4. 警惕"竞品归因偏差"

### 业务逻辑结合边界

1. 可以结合行业通用逻辑（公开规则/标准流程）
2. 不可以结合未验证的业务细节
3. 不确定时标注"需业务方验证"
4. 宁可少说不可说错

### 区分主动需求与验证反馈

1. 主动需求：用户自发描述的痛点（有情绪和经历）→ 四力更可信
2. 验证反馈：研究员展示新概念后的回应 → L偏高A偏低
3. 报告中必须区分两类，优先级排序时主动需求权重更高

### 场景时效性判断

1. 从时间线索判断场景时段
2. 近期vs早期冲突时以近期为准
3. 早期数据可用来构建趋势
4. 无法判断时默认"当前有效"但标注

### Skill自演化（元规则）

当用户在使用本Skill过程中指出了一个新的踩坑、纠正了一种错误做法、或提出了一个本Skill未覆盖的要求时——**不要只在本次对话里临时修补，必须把这条经验固化回Skill本身**：

1. 把新规则补进对应阶段的正文 + 速查表（R/Y/G编号）
2. 把"为什么"（这次踩的坑）写进「附录B：硬规则踩坑来源档案」
3. 如涉及可程序化校验，补一个脚本进「十、Python验证脚本集」
4. 升级version并在CHANGELOG记录

> 来源：同一类错误（如去重失败、半翻译残留）在不同项目里反复出现，根因是"修了这次没沉淀"。Skill的价值在于把一次性的纠错变成永久的免疫力——用户提醒一次，规则就该长在Skill里，而不是靠下次记得。
