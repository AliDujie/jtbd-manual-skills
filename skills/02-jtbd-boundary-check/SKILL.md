# JTBD 项目边界判断

## 触发场景

- 业务方给了一个需求，研究者要判断该不该用 JTBD
- 项目启动前的方法选型
- 已经在做 JTBD，中途怀疑方向不对
- 团队 leader 评审下属提上来的 JTBD 项目提案

## 核心能力

### 能力一：五问自检

对输入的项目问题，用五问打分：

1. 问题落脚点：用户挣扎 / 业务指标
2. 挣扎执行方：产品自身 / 上游服务商 / 政策规则
3. 需要产出：该给谁做什么 / 市场规模
4. 研究对象：外部用户 / 内部员工
5. 期望产出：具体功能建议 / 深层机会挖掘

输出：五问对错勾表 + 适用性评级（强推荐 / 建议做 / 谨慎做 / 不建议做）

### 能力二：三类不适用辨识

识别以下三类"JTBD 答不了"的场景：

- **供给侧决定**：用户不满发生在你界面里，但决策不在你手上
- **市场规模/竞争定位**：宏观口径问题，深访小样本给不出答案
- **组织行为/协作机制**：内部员工问题，本质是激励机制而非用户挣扎

### 能力三：三类锋利场景识别

反向确认 JTBD 特别锋利的三类：

- **切换时刻分析**：Switch 访谈是 JTBD 家专利
- **补偿行为挖掘**：JTBD 最独特的贡献
- **情境驱动分层**：比人口学分层更精准

### 能力四：替代方法建议

若判断不适用 JTBD，推荐更合适的方法：

- 漏斗诊断问题 → 数据看板 + 埋点分析
- 市场规模问题 → 行业报告 + 支付数据分析
- 组织行为问题 → Congruence Model / 7S 组织诊断
- 功能可用性问题 → 可用性测试 / 卡片分类

## 依赖底层 skill

不依赖底层执行 skill——这是判断力 skill，纯规则驱动。

## 输出形态

- 一份"项目适用性评估表"（Markdown 表格）
- 一段判断依据的叙述性说明（3-5 句）
- 若不适用，给出至少 2 个替代方法建议

## 与其他 skill 的关系

- **前置**：无（本 skill 是全流程第一站）
- **后置**：适用性通过后 → jtbd-hypothesis-decompose（关卡 1 拆假设）
- **旁支**：不适用时 → 建议改用其他非 JTBD 方法

## 使用示例

用户输入："业务方让我看看用户为什么流失，我该不该用 JTBD？"

输出：
1. 五问评估表
2. 结论：如果流失口径是"从平台完全离开"→ 需先做数据看板定位流失环节；如果是"某功能不再使用"→ JTBD 主场
3. 分岔建议
