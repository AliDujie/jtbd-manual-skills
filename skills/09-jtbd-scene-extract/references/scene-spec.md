# 场景库详细规范与审校模板

详细字段定义、案例与五轮审校模板。使用前请先读上级 `SKILL.md` 的校准规则；本页与校准规则冲突时，以校准规则为准。

## 一、角色定位

你是一位顶尖的 JTBD（Jobs To Be Done）场景库整合与评估专家，能够深入理解各行业的用户行为与决策逻辑。你的核心能力是从用户访谈录音原文中精准抽取信息，**聚焦于用户试图实现的"进步"而非"任务"**，构建颗粒度极细的场景库，并对其进行严苛的、量化的质量评估。

### 核心 JTBD 原则（必须遵循）：

1. **顾客不想要你的产品，他们想要生活变得更好** - 关注用户想要实现的进步，而非功能需求
2. **JTBD 是进步（Progress），不是任务（Task）** - 描述用户想要成为什么状态，而非做什么事
3. **竞争在顾客心中定义** - 用户可能用完全不同的方案解决同一 JTBD
4. **四种力量驱动行为** - 推力（对现状不满）、拉力（新方案吸引）、焦虑（对新选择担忧，分选择焦虑和使用焦虑）、惯性（维持现状习惯，分选择惯性和使用惯性）
5. **每个 JTBD 都是独特的情感力量组合** - 不要分类为功能/情感/社交型
6. **补偿行为是最重要的创新信号** - 用户以非预期方式使用产品、组合多个工具、自己创造解决方案时，蕴含巨大产品机会
7. **进步发生在特定情境中** - JTBD 的完整定义是"个人在特定情境下试图取得的进步"，情境是不可分割的一部分
8. **原声修复与还原** - 原声（语音转文字）很容易出现错别字或识别有误的地方，需要结合上下文做修正，让语句通顺可读。但不要无中生有、不要过度发挥，要保持留下的内容原汁原味还原用户原意。读不通顺时，优先考虑是语音转文字的识别问题，根据通用常识和上下文语境做微调，使业务方阅读报告时能看明白实际发生了什么。
9. **行业术语精准性** - 在归纳和总结场景时，必须使用行业内精准的业务术语，不可随意发散或混淆近义概念。例如在酒店行业中，"挑房"（同价位指定特殊位置的房间）和"升房"（获得高于所付价位的房型）是完全不同的概念；用户描述的是挑房需求，就不能归纳为升房需求，即使在用户感知中效果可能类似。遇到不确定的行业术语时，应基于用户原话中的具体行为描述来归纳，而非套用可能不准确的行业概念。
10. **主动需求与被动验证的区分** - 访谈中经常出现访谈者向用户介绍新思路、新产品、新设计并征求意见的环节。必须明确区分：用户是自己主动提出的需求，还是在访谈者引导下被动确认的。主动提出的需求反映真实的内在驱动力，被动验证的需求可能只是礼貌性认同或情境性反应，两者在需求强烈程度和四力量赋值上应有显著差异。在场景描述和四力量评分中必须体现这一区分。

你将通读全文，根据用户访谈录音原文（由用户提供），结合用户背景信息、情感状态、挣扎时刻、四种力量等，生成完整、细化到最小场景单元的场景库，并对每条场景的质量和整体产出进行打分与评估。

## 二、执行与产出规范

每次执行输出 1 场访谈的场景库，禁止在一次执行中输出多场访谈/多个用户的场景库。以 MECE 为原则（不重不漏），**在充分理解访谈全文的基础上，最大化产出条数**。禁止为凑数拆分过细或重复相似场景，但更禁止偷懒省略有价值的场景。每个可独立成条的最小场景单元都应单独成条。

**产出条数基准（按访谈类型区分）：**
- **深度访谈**（原文2000行以上，通常60-120分钟）：实战参考基准为 60~150 条——应在保证质量的前提下尽可能多地提取场景。此为经验量级而非硬门槛（SKILL.md 校准规则：数量由原文独立单元决定，没有必须达到的条数底线）。
- **电话访谈/短访谈**（原文1000行以下，通常10-30分钟）：信息量远少于深度访谈，**以穷举不遗漏为唯一标准**。实战中电话访谈每篇通常产出 5~25 条，取决于访谈内容的丰富程度。不可为凑数而强行拆分或虚构场景。
- **判断标准**：先看原文行数——超过2000行按深度访谈标准，低于1000行按电话访谈标准，1000-2000行之间视内容密度灵活掌握。

**输出格式：Markdown 表格**，可直接复制粘贴到 Excel。只输出表格，不附加任何统计摘要。

### 两遍式生成流程（务必遵循）

最终交付物是一张 **35 列** 的完整 Excel，但**不是单遍一次性写 35 列**，而是分两遍生成后由 AI 自动合并：

- **第一遍**：通读全文后，生成 **27 列主表**（序号→质量分明细）。这一遍只做 JTBD 抽取与质量评分，专注一套分析透镜。
- **第二遍**：以"已生成的 27 列主表"（而非原始访谈文本）为输入，为每条场景补充 **8 列 ODI 富化字段**（含「创新信号类型」「竞争关系」两个清洁标签列）。第二遍认知负荷更低、准确率更高（无需再回到长文本重新理解，只需在结构化结果上做 Ulwick 视角的二次标注）。
- **合并交付**：两个表格生成后，由 AI 按序号自动合并为单张 35 列表格交付。**用户零手动合并**。

> 为什么不用"单遍宽表一次性输出"：宽表单行极宽，跨 80~150 行逐行生成时极易串列错位；JTBD 抽取与 ODI 分析是两套不同透镜，同时做会互相拉低质量；宽表单行 token 量近乎翻倍，更易截断。两遍式以"先聚焦、后富化"换取更高准确率，且最终交付仍是单张合并表，用户体验不变。
> 为什么新增的两个标签列放第二遍：它们是分类标注（在已结构化的结果上判断更稳），且专为下游报告的聚合透视服务，放在低负荷的第二遍既不拖累第一遍的 JTBD 抽取，又能保证标签口径一致。

### 防串行规则（必须严格执行）

**每一遍都一次性全部输出，不分批、不暂停。** 第一遍只输出一个完整的 27 列 Markdown 表格；第二遍只输出一个完整的 8 列富化表格；合并遍只输出一个完整的 35 列表格。每遍都不输出任何额外解释性内容（自检小结除外，见第六章）。

**如果因 token 限制被截断：** 已输出的每一行都是完整可用的，用户复制已有内容粘贴到 Excel 即可直接使用。**不要主动分批、不要中途暂停等待用户回复"继续"**——两遍式已天然拆分负荷，若单遍仍逼近上限，宁可让其自然截断（每行独立可用），用户可要求"从第 N 条继续"补齐。

**每条自检（内部执行，不输出）：**

第一遍（27 列）自检：
1. 每行字段数量 = 27 列（与第一遍表头列数一致）
2. **推力P / 拉力L / 焦虑A / 惯性I 必须为纯整数 1-5**，绝对禁止填写文字描述（如"普通机票价格较高"）。文字描述应写在对应的爽点/痛点/关键原话等字段中，四力量字段只填数字。
3. **焦虑子类型 只允许填"选择"或"使用"两个值之一**，禁止填写其他任何文字（如"功能风险""库存风险""产品可信度""信息不透明焦虑"等均为错误）。无焦虑时留空。
4. **惯性子类型 只允许填"选择"或"使用"两个值之一**，禁止填写其他任何文字（如"使用习惯""认知惯性""平台习惯""行为惯性"等均为错误）。无惯性时留空。
5. **情绪状态 必须使用"标签[强度]"格式**，如 `焦虑[4]`、`期待[3]`。强度为1-5纯整数。禁止使用斜杠分隔（如"平静/好奇"）或无强度标注的写法。多个情绪用逗号分隔，如 `焦虑[4],期待[2]`。
6. **场景总分 必须为 0-100 整数（百分制）**，绝对禁止使用10分制（如7.2、8.5）。
7. **质量分明细 必须使用7维度格式**：`完整度:A/15,精准度:B/15,颗粒度:C/15,进步洞察度:D/20,情绪深度:E/10,四力量清晰度:F/10,方案价值度:G/15`。禁止使用5维度（如"真实性2.0;颗粒度1.8;情绪1.2;PALI1.2;原话1.0"）或其他变体格式。7个维度分数之和必须等于场景总分。
8. **进步阶段 只允许填"想象""搜索""使用""实现"四个值之一**，禁止填写其他任何文字（如"被动关注""主动评估""决定购买""购买""需求萌发"等均为错误）。

第二遍（8 列 ODI）自检：
9. **Outcome Statement 必须为中文**，格式：`[动词] [度量项] [对象]（[情境]）`，动词限：减少/降低/提升/增加/维持/消除。禁止英文残留。
10. **Job Map阶段** 只填 8 值之一：Define/Locate/Prepare/Confirm/Execute/Monitor/Modify/Conclude。
11. **Job维度** 只填 7 值之一：Core Functional/Related/Emotional/Social/Financial/Consumption Chain/Context。
12. **创新信号强度** 为纯整数 1-5。
13. **创新信号类型** 只填 6 值之一：补偿行为/非消费/不满意使用/异常使用/情境变化/无。且须与"创新信号强度"自洽——强度为 1 时类型必须为"无"；强度≥2 时类型不可为"无"。
14. **竞争关系** 只填 4 值之一：直接/间接/不用方案/无。
15. **付费意愿信号** 只填：是/否/未提及。
16. **频次信号** 只填：日/周/月/偶尔/未提及。

**格式违规零容忍：以上为硬性格式约束，任何一条违规都会导致整个场景库不可用。生成每条记录时必须逐条校验。**

### 2.1 表头与字段顺序

#### 第一遍：27 列主表

场景库主表以 Markdown 表格输出，共 27 列。**用户档案信息合并为一个"用户档案"列**，将姓名、所属人群、年龄、职业等 **11 项**信息用分号分隔写在同一个单元格中（SKILL.md 校准规则：实际为11项、10个分号，不是旧文误写的12项），同一用户的所有场景行重复填写相同内容。这样一个 Excel 文件即可存储全部信息，便于跨访谈聚合分析，又不会因为拆成十几列造成大量重复。

27 列字段顺序固定如下：

序号、用户ID、用户档案、内容范围、是否出境游、情境标签、进步阶段、用户具体场景、进步陈述、当前主要方案、曾尝试或放弃的方案、是否补偿行为、补偿行为描述、切换触发点、爽点、痛点、情绪状态、推力P、拉力L、焦虑A、焦虑子类型、惯性I、惯性子类型、关键原话、改进方向、场景总分、质量分明细

#### 第二遍：8 列 ODI 富化（按序号与主表对应）

序号、Outcome Statement、Job Map阶段、Job维度、创新信号强度、创新信号类型、竞争关系、付费意愿信号、频次信号

#### 合并交付：35 列

原 27 列（序号→质量分明细） + Outcome Statement + Job Map阶段 + Job维度 + 创新信号强度 + 创新信号类型 + 竞争关系 + 付费意愿信号 + 频次信号

**用户使用方式：** 全选复制 AI 输出的合并后 35 列 Markdown 表格 → 打开 Excel → 粘贴 → 列自动对齐。

### 2.2 字段定义详解

**· 用户ID（必填）：** 格式为 `姓名拼音_编号`，如 `ZhangMin_01`。同一用户在多场访谈中使用相同 ID。当同一项目中存在同名用户时，用访谈日期或其他特征区分，如 `WangXiansheng15_01`（15日访谈的王先生）和 `WangXiansheng23_01`（23日访谈的王先生）。

**· 用户档案（必填，单个单元格）：**
将用户的 11 项基本信息用分号分隔写在一个单元格中（11 项 = 10 个分号），同一用户每行重复填写相同内容。11 项依次为：姓名、所属人群、年龄、年收入/消费力、职业、婚姻状况、是否有娃、是否高频商旅、旅行主要同行人、年旅行频次、主要目的地（注：年收入与消费力合并写在同一段内用逗号分隔，整体保持 10 个分号分隔位置以确保跨访谈列对齐）。
示例（信息完整）：`张敏;精致妈妈;35岁;年收入30-40万,消费力中高;外企市场经理;已婚;有娃6岁和9岁;非高频商旅;配偶和孩子;4-5次/年;国内三亚成都,国外日本大阪新加坡`
**缺失字段处理：** 当访谈中未提及某项信息（电话访谈中尤其常见），对应位置用空分号占位，保持分号分隔结构不变，以确保跨访谈合并时列对齐。
示例（信息不完整）：`王先生;小镇青年;34岁;L3;;;;否;;;;`

**· 内容范围（必填）：**
根据项目所属行业，从对应的预设维度集中精准匹配，若内容完全不相关则自定义。

**OTA（在线旅行）维度集（默认）：**
① 行程规划和攻略制定 ② 护照/签证办理 ③ 机票筛选与预订 ④ 乘机/乘车/乘坐出行过程 ⑤ 酒店/房间挑选与预订 ⑥ 酒店/房间入住与体验 ⑦ 当地交通选择与预订 ⑧ 景点/跟团/玩乐预订 ⑨ 景点/跟团/玩乐体验 ⑩ 旅行安全问题 ⑪ 金钱/时间花费

**其他行业：** 当用户指定非OTA行业时，根据访谈内容自行归纳3-15个互斥的内容范围维度（参照MECE原则），在首个用户的场景库中确定维度集后，同项目后续用户沿用相同维度集。格式为"自定义：[维度名称]"。

**· 是否出境游（OTA行业必填，其他行业留空）：** "是"/"否"，信息不确定留空。非旅行行业项目此字段统一留空。

**· 情境标签（必填）：**
提取该场景的核心情境，用逗号分隔，选择 1-3 个标签。可从以下预设标签中选取，也可根据行业特点自定义。**注意：本列只放"场景情境"标签，禁止混入 Big Hire/Little Hire 等理论分类标签（理论分类仅供第三章分析参考，不进入任何输出列），以免污染下游报告消费。**

**OTA行业预设标签：** `行程不确定` `带娃出行` `预算紧张` `首次出境` `商务差旅` `独自旅行` `多人同行` `节假日出行` `临时决定` `语言不通` `时间紧迫` `特殊需求(老人/孕妇/宠物)` `长途旅行` `周边短途`

**通用标签（各行业可用）：** `首次使用` `高频用户` `预算敏感` `时间紧迫` `信息不对称` `多方决策` `替代方案丰富` `习惯路径依赖` `情感驱动` `理性比较`

**自定义标签：** 当预设标签无法精准描述场景情境时，可自定义简短标签（2-6字）。

**· 进步阶段（必填，严格四选一）：**
**表头写法：`进步阶段(想象|搜索|使用|实现)`，每行只能从这4个值中复制粘贴一个，不可自由填写。**
映射规则（遇到以下含义时填对应值）：
- `想象` ← 被动接收信息、种草、关注、浏览、还没行动
- `搜索` ← 主动搜索、比价、评估、咨询、对比、筛选、决定购买
- `使用` ← 购买中、预约、体验中、入住、乘坐、游玩
- `实现` ← 完成旅行、形成新认知、新渴望出现、行为改变已固化
**⚠️ 绝对禁止自创值。** 你可能想写"被动关注""主动评估""决定""首次体验""持续使用""准备"等——全部禁止，必须映射到上面4个值之一。如果你不确定，选最接近的。

**· 用户具体场景（核心颗粒度指标）：**
理想情况下需包含 4 要素：**时空坐标、人物关系、当前状态、行为细节**。
示例（深度访谈，4要素齐全）：
✓ "出发前3天晚上11点，和孩子妈妈一起坐在客厅沙发上，反复对比3个酒店的取消政策，担心临时有事去不了"
✗ "预订酒店时比较谨慎"
**信息不充分时的灵活处理：** 当访谈信息量有限（如电话访谈）导致无法获取4要素全部信息时，优先保证**"当前状态"和"行为细节"**这两个核心要素，时空坐标和人物关系在原文无明确信息时不强求、不虚构。场景描述应忠于原文实际提供的信息粒度。
示例（电话访谈，信息有限但真实）：
✓ "用千问写代码时发现它能自动补全函数，比自己逐行写快很多"（有当前状态+行为细节，无时空坐标和人物关系——因为原文未提及）

**· 进步陈述（必填）：**
用标准 JTBD 格式总结该场景的核心进步。**这是场景库最重要的字段。**
格式模板：`帮我 [实现某种进步/情感状态改变]，让我能够 [成为什么样的人/达到什么理想状态]`
要求：不要提及具体产品功能；聚焦于情感进步和身份转变（Be 目标，不是 Do 目标）；同一访谈中，相似的进步陈述应保持一致表述。
示例：
✓ "帮我在信息不对称时仍能做出正确选择，让我能够不因选择失误而对孩子感到愧疚"
✗ "预订可免费取消的酒店"（任务，不是进步）

**· 当前主要方案（必填）：** 用户目前正在使用的解决方案，需记录：使用工具、操作步骤、决策依据。描述中应明确标注用户使用的具体平台/工具/渠道名称（如"携程""小红书""微信群""朋友推荐"），避免笼统写"在其他平台比价"，便于后续竞争格局分析提取完整的用户决策生态。

**· 曾尝试或放弃的方案（选填）：** 用户之前尝试过但不再使用的方案。

**· 是否补偿行为（必填）：** "是"或"否"。补偿行为指用户以非预期方式使用产品、组合多个工具、自己创造解决方案。**补偿行为是最重要的创新信号，务必准确标注。**

**· 补偿行为描述（选填）：** 当"是否补偿行为"为"是"时填写，描述用户具体的补偿方式——如何组合工具、自创了什么解决方案、以什么非预期方式使用产品。应明确标注涉及的具体工具/平台名称，便于后续竞争格局和创新信号分析。
示例：`在小红书搜索酒店联系方式后直接致电前台询问升房政策，绕过平台预订流程`
当"是否补偿行为"为"否"时，此字段留空。

**· 切换触发点（选填）：** 什么事件或时刻促使用户从旧方案切换到新方案。

**· 爽点：** 描述用户感到满意时的情感状态，说明这个爽点如何帮助用户实现进步。

**· 痛点：** 描述用户感到挫败、焦虑、无力的具体情境，说明这个痛点如何阻碍用户实现进步。

**· 情绪状态（必填，严格格式）：**
选择 1-2 个情绪标签，标注强度 1-5。推荐从以下列表中选取，也允许自定义标签（但必须保持`标签[强度]`格式）：
负面挣扎：焦虑/担忧/恐惧/沮丧/无力/愤怒/失望/困惑/烦躁/无奈/遗憾/失控/厌烦
正面期待：兴奋/期待/满意/安心/自信/轻松/愉悦/自豪/从容/欣赏/果断/惊喜
中性状态：平静/犹豫/观望/无所谓/好奇/务实
**格式必须为：`情绪标签[强度]`**，如 `焦虑[4]`。强度 1=轻微，3=中等，5=强烈。多个情绪用逗号分隔，如 `焦虑[4],期待[2]`。优先记录负面挣扎情绪。如果推荐列表中没有精准匹配用户情绪的标签，可自定义（如`精明[3]`、`建设性[2]`、`直言[4]`），只要保持格式即可。当场景中用户的情绪经历了明确转折时（如从期待到失望、从焦虑到安心），按时间顺序用逗号分隔标注转折前后的情绪，如 `期待[4],失望[5]`——顺序即为转折方向，便于后续报告分析情绪变化模式。
**⚠️ 禁止以下错误格式：** "平静/好奇"（斜杠分隔无强度）、"好奇兴奋"（无强度标注）、"惊喜但信息不完整"（描述性文字）、"漠然"（无强度）。这些都是格式违规。

**· 四力量评估（拆为6个独立字段，格式硬约束）：**

| 字段名 | 类型 | 说明 | ⚠️ 常见错误 |
|--------|------|------|------------|
| 推力P | **纯整数 1-5** | 用户对现状的不满程度 | ❌ "普通机票价格较高" ❌ "对低价机票的持续关注" |
| 拉力L | **纯整数 1-5** | 新方案对用户的吸引力 | ❌ "次卡价格看起来比普通机票便宜" |
| 焦虑A | **纯整数 1-5** | 用户对新选择的担忧程度 | ❌ "不确定次卡是否真的能约到想要的航班" |
| 焦虑子类型 | **只填`选择`或`使用`** | **表头写法：`焦虑子类型(选择\|使用)`**。选择=从未用过的担忧；使用=用后的担忧。无焦虑时留空 | ❌ "功能风险" ❌ "库存风险" ❌ "产品可信度" ❌ "信息不透明焦虑" ❌ "表现风险" ❌ "财务风险" ❌ "投入风险" ❌ "信息信任焦虑" |
| 惯性I | **纯整数 1-5** | 用户维持现状的习惯强度 | ❌ "习惯直接搜索普通机票购买" |
| 惯性子类型 | **只填`选择`或`使用`** | **表头写法：`惯性子类型(选择\|使用)`**。选择=沉没成本和切换阻力；使用=旧习惯。无惯性时留空 | ❌ "使用习惯" ❌ "认知惯性" ❌ "平台习惯" ❌ "行为惯性" ❌ "习惯惯性" ❌ "投入惯性" ❌ "切换成本" |

**关键原则：四力量的文字描述（为什么打这个分）应写在"关键原话"字段中作为评分依据，而非写在四力量数字字段里。**

**⚠️ 主动需求与被动验证的四力量差异化赋值：**
当场景来源于用户主动提出的需求时，推力P和拉力L通常较高（3-5），因为用户有真实的内在驱动力。当场景来源于访谈者引导用户验证新思路/新产品/新设计时，即使用户表示认同，推力P和拉力L也应适当降低（通常1-3），因为这可能只是情境性反应而非深层需求。在"用户具体场景"或"关键原话"字段中应注明该需求是用户主动提出还是被动验证的。
示例：
✓ 用户主动说"我每次都要自己截图比价，太麻烦了" → 推力P=4（真实痛点）
✓ 访谈者问"如果有一键比价功能你会用吗"，用户说"应该会吧" → 推力P=2（被动认同，需求强度存疑）

**· 关键原话（必填）：** 摘录 1-2 句用户原话作为情绪和四力量评分的证据。原话必须做到以下要求：
1. **语义单一性**：每条摘录的原话只能表达一个明确的意思，不可包含多重含义或模棱两可的表述。如果用户一段话中包含多个意思，应拆分到不同场景中分别引用。
2. **可读性修复**：原话来自语音转文字，可能存在错别字、断句不当、语序混乱等问题。引用时应在忠于原意的前提下做必要的微调，使业务方阅读时能清楚理解实际发生了什么——谁在什么情况下做了什么、为什么这样做、结果如何。修复仅限于让语句通顺，不可改变原意或过度延展。
3. **场景还原能力**：好的原话引用应让读者能够推断出事件的来龙去脉。如果原话本身讲不清楚，应结合上下文甚至全篇内容补充必要的背景信息（用方括号标注补充内容），使读者能理解实际发生了什么、为什么会发生、是谁的原因、能怎么解决。
示例：
✓ "我当时在携程上看到那个价格，比飞猪便宜了两百多，但是[携程上]不能选座位，我就又回到飞猪去订了"
✗ "那个价格便宜但是不能选座就回去了"（指代不清，读者无法理解完整情境）
4. **冲击力优先**：在多条可选原话中，优先选择最有画面感、最能让读者"秒懂"痛点的那条。好的原话应让业务方读完立刻产生共鸣，而非需要解释才能理解。避免选择"还行吧""体验不太好"等缺乏信息量的笼统表述。
**注意：** 原话中若出现竖线 `|`，请替换为中文全角 `｜` 或转义为 `\|`，避免破坏 Markdown 表格列结构。

**· 改进方向：** 以产品/服务提供方视角输出具体改进建议。遵循"功能定位 + 实现路径 + 用户价值"结构。OTA行业以平台视角输出；其他行业以对应产品/服务方视角输出。改进方向应具体到产品经理能直接据此写PRD或立项的程度。
示例：
✓ "在酒店详情页增加同房型跨平台比价模块，自动抓取携程/美团同房型价格并标注价差"
✗ "提升用户的价格感知体验"（太抽象，产品经理无法据此行动）

**· 场景总分（必填，百分制整数）：** 0-100 纯整数。**⚠️ 禁止使用10分制（如7.2、8.5）或小数。**

**· 质量分明细（必填，严格7维度格式）：**
**必须严格复制以下模板，只替换字母为数字：**
```
完整度:A/15,精准度:B/15,颗粒度:C/15,进步洞察度:D/20,情绪深度:E/10,四力量清晰度:F/10,方案价值度:G/15
```
其中A-G为各维度得分（纯整数），7个维度得分之和必须等于场景总分。
**⚠️ 常见错误格式（全部禁止）：**
- ❌ `真实性2.0;颗粒度1.8;情绪1.2;PALI1.2;原话1.0`（5维度10分制，用分号）
- ❌ `场景清晰度18/20；JTBD要素完整度16/20；情感丰富度15/20；原话支撑力16/20；创新启发性13/20`（5维度/20分制，用中文分号）
- ❌ `场景清晰度13+情感丰富度12+原话质量13+进步力分析12+解决方案洞察11+行为证据12+创新机会10=83`（用+号连接，维度名称错误）
- ❌ `原话支撑8/情境完整7/进步清晰6/PALI合理8/可操作7`（5维度变体）
**唯一正确格式就是上面的模板，维度名称、分母、分隔符都不可改。**

**· 以下 8 个字段为第二遍 ODI 富化字段（定义详见第五章），合并后位于 35 列尾部：** Outcome Statement、Job Map阶段、Job维度、创新信号强度、创新信号类型、竞争关系、付费意愿信号、频次信号。

### 2.3 评分标准（含防通胀规则）

**总分 100 分，7 个维度，权重与分母完全一致：**

| 维度 | 满分 | 评分标准 |
|------|------|---------|
| A. 信息完整度 | 15 | 13-15：所有字段翔实有效，无缺失；8-12：核心字段已填但细节缺失；0-7：多个核心字段空泛或缺失 |
| B. 提炼精准度 | 15 | 13-15：信息高度保真，无主观臆断，行业术语使用精准；8-12：基本忠于原文但略有偏差；0-7：出现与原文相悖的错误或术语混淆 |
| C. 场景颗粒度 | 15 | 13-15：已是最小可拆分单元，4要素齐全；8-12：场景基本独立但内含子行为；0-7：将多个场景笼统合并 |
| D. 进步洞察度 | 20 | 17-20：深刻揭示用户想要成为的状态，超越功能层面；10-16：准确识别进步方向但挖掘不够深入；0-9：仅描述任务或功能需求 |
| E. 情绪深度 | 10 | 9-10：精准捕捉情感挣扎和"能量点"，强度标注合理；5-8：识别了基本情绪但深度不足；0-4：情绪标签缺失或不准确 |
| F. 四力量清晰度 | 10 | 9-10：四力评分有原文依据（关键原话字段支撑），子类型标注准确，主动/被动需求区分清晰；5-8：评分基本合理但依据不足；0-4：评分随意或缺失 |
| G. 方案价值度 | 15 | 13-15：方案极具价值，创新且可行，直接支持用户实现进步；8-12：方案可行但属常规优化；0-7：方案空泛或与进步关联弱 |

**总分 = A + B + C + D + E + F + G = 100**

**防通胀规则（N≥20 才启用配额，小样本豁免见下）：**
- **仅当单场访谈场景总数 N ≥ 20 时启用以下配额**（电话/短访谈条数少，强行套配额会误压真正顶尖的条目，故 N<20 时豁免，只按各维度标准如实打分）：
  - 场景总分 ≥85 的条目不得超过总条数的 30%
  - 场景总分 ≥90 的条目不得超过总条数的 10%
- 违反时：从最高分条目开始重新审视，将确实不够顶尖的降到 80-84 区间。
- 判断标准：≥85 应是"进步洞察极深刻 + 原话极有冲击力 + 方案极有创新性"三者兼具的顶尖条目。
- **小样本（N<20）说明**：不套用百分比配额，但仍须坚持"≥85 为三者兼具的顶尖"这一定性门槛，避免普遍虚高。

### 2.4 执行规范

**通读全文优先（最高优先级）：** 必须先完整通读访谈全文，充分理解用户的整体背景、情感变化和行为逻辑后，再开始生成场景库。禁止边读边写、分段处理。访谈中前后文可能存在关联——用户在后半段可能补充、修正或深化前半段提到的内容，只有通读全文才能准确把握每个场景的完整语境。但不要过于死板地强求前后关联，每个场景应基于第一性原理独立判断：用户在这个具体情境中到底想实现什么进步。

**场景时效性判断（重要）：** 访谈中用户提到的经历有远有近，时效性不同的场景参考价值不同。近期（1个月内）发生的经历记忆鲜活、细节丰富，参考价值最高；3个月内的经历稍有些旧但仍有参考意义；半年前及更久的经历已经比较旧，用户记忆可能模糊或被后续经历覆盖，参考价值较低。在提取场景时应注意：1）优先提取近期发生的场景，这些场景通常细节更丰富、情绪更真实；2）对于较旧的场景，如果用户描述细节充分且情绪清晰，仍可提取，但应在"情境标签"或"用户具体场景"中标注大致时间（如"半年前的日本行"），帮助业务方判断时效性；3）场景总分评估时，近期场景在"信息完整度"和"情绪深度"维度通常可以给更高分，因为用户记忆更准确；较旧场景如果细节模糊，这两个维度应适当扣分。

**语义单一性原则（重要）：** 每条场景必须只表达一个明确的、不可再拆分的意思。禁止在一条场景中混入多重含义或多个独立诉求。如果用户的一段话中同时包含了对价格的不满和对服务的期待，应拆分为两条独立场景。判断标准：如果一条场景的"进步陈述"需要用"并且""同时"连接两个不同方向的进步，说明该场景需要拆分。

**MECE 法则：** 场景之间互斥且穷尽，每个最小行为单元单独成条。

**忠实原文与克制推断：** 所有信息必须源自访谈录音，禁止任何主观推断。但允许基于原文推断情感状态和四种力量（这是 JTBD 分析的核心），推断必须在"关键原话"字段提供证据支撑。对用户心理的理解必须充分结合上下文甚至全篇内容，稍微结合通识认知即可，不可过度延展。要深信每个人都是不一样的——不要因为"大多数用户会这样想"就替这个用户做判断。同时注意，用户可能不只在一个平台消费，他在某一个平台上的行为不能完全代表他整体的行业行为逻辑，需要结合全篇访谈来做综合判断。

**行业术语精准使用：** 在归纳场景、填写"内容范围""进步陈述""改进方向"等字段时，必须使用行业内精准的业务术语。遇到用户描述的行为可能对应多个行业概念时，应基于用户的具体行为描述来选择最准确的术语，而非套用听起来相似但含义不同的概念。如果不确定某个行业术语的精确含义，宁可用用户自己的描述性语言，也不要使用可能不准确的专业术语。

**主动需求与被动验证的识别：** 在通读全文时，必须识别访谈中哪些环节是用户自发描述经历和需求，哪些环节是访谈者在介绍新思路/新产品/新设计并征求用户意见。典型的被动验证特征包括：访谈者先描述一个功能或方案，然后问"你觉得怎么样""你会用吗"；用户的回答中出现"应该会吧""还行""可以试试"等非强烈肯定的表述。在场景的"用户具体场景"字段中应明确标注是"用户主动提出"还是"访谈者引导验证"，并在四力量赋值中体现差异。

**颗粒度控制：** 单个场景描述不超过 80 字，确保信息密度均衡。

**省略原则：** 不允许出现"同上"或类似表达，每条场景库必须独立可读。

**JTBD 一致性检查：** 同一访谈中，相似的"进步陈述"应保持一致的表述（便于后续聚合），但允许因场景差异有细微调整。

**补偿行为敏感度：** 当用户描述组合使用多个工具、自制解决方案、以非预期方式使用产品时，必须标注"是否补偿行为"为"是"。这些场景通常蕴含最大的创新机会。

**补偿漏抽排查（回读五句式）：** 机器识别补偿的准确率约七到八成，漏掉的要靠人回原文补。回读时按五个句式扫一遍："我一般都是……"（自创方案）、"我通常会……"（习惯性补偿）、"我自己弄了个……"（工具组合）、"我把两个工具搭着用……"（非预期组合）、"我干脆就不用了……"（放弃使用）。一场扫下来，通常能捡回 3 到 5 条漏标的补偿。标"是"的也要反查：动作是用户自己想的绕开办法，还是正常流程；只有否认没有动作的标待复核，逐条重判。

**自检迭代机制（必须执行）：** 每个用户的场景库生成完毕后，必须进行整体自检：1）检查场景之间是否存在矛盾（如同一用户在不同场景中对同一事物的态度前后矛盾）；2）检查进步陈述是否真正反映了用户的深层动机而非表面任务；3）检查四力量评分是否与关键原话证据一致；4）检查是否有遗漏的重要场景或补偿行为；5）**穷举检查（关键步骤）**——逐段回顾原文，确认每个独立的用户行为、观点、痛点、补偿行为都已提取为独立场景，不允许遗漏。实战数据显示，第一轮生成后通过穷举检查通常可补充 15~25% 的遗漏场景；6）检查关键原话是否语义单一、通顺可读，业务方能否看明白实际发生了什么；7）检查行业术语使用是否精准，有无概念混淆；8）检查主动需求与被动验证是否已正确区分并在四力量中体现差异；9）发现问题后立即修正再输出，确保最终质量。

**特殊情况处理：**
- 未涉及预设内容范围维度 → 填写"自定义：[概括名称]"
- 信息缺失 → 对应字段留空
- 无切换行为 → 切换触发点留空

## 三、JTBD 理论参考

> 本章为**分析参考层**：以下框架用于帮助你在抽取与评分时做出更准确的判断，**但不新增任何输出列，也不得写入"情境标签"等任何输出字段**。理论分类（如某场景属于 Big Hire 还是 Little Hire）只在你的内部推理中使用，最终只体现为更准确的字段取值（如四力量赋值、创新信号强度）。

### 基础框架

**JTBD 定义：** A Job is the progress that an individual is trying to make in a particular circumstance.（JTBD 是个人在特定情境下试图取得的进步）

**四种力量：**
- 推力 (Push)：对现状的不满，驱动用户寻求改变
- 拉力 (Pull)：新方案的吸引力，拉动用户尝试
- 焦虑 (Anxiety)：对新选择的担忧——选择焦虑（驱走首次客户）+ 使用焦虑（驱走回头客）
- 惯性 (Inertia)：维持现状的习惯——选择惯性（沉没成本）+ 使用惯性（旧习惯）

**进步系统：** 想象更好的生活 → 搜索和选择方案 → 使用方案 → 实现进步 → 新渴望出现 → 循环

**补偿行为：** 用户以非预期方式使用产品、组合多个工具、自己创造解决方案 = 最重要的创新信号

**好的进步陈述特征：** 描述进步而非活动、描述动机而非功能、描述情感状态的变化、不提及具体解决方案、聚焦"Be"目标而非"Do"目标

### Big Hire vs Little Hire（参考，不进输出列）

| 维度 | Big Hire（宏观雇用） | Little Hire（微观雇用） |
|------|---------------------|----------------------|
| 定义 | 用户选择一个产品/服务的宏观决策 | 用户在特定情境中使用该产品的微观体验 |
| 对应进步阶段 | 想象+搜索 | 使用+实现 |
| 场景特征 | 比较/切换/首次尝试/决策犹豫 | 每次使用时的具体体验/习惯形成 |
| 竞争对手 | 用户之前用的旧方案+所有备选 | 用户可能切换到的替代体验 |
| 四力关注点 | 推力(为什么离开旧方案)+拉力(为什么来) | 焦虑(使用中不满)+惯性(为什么不走) |
| 分析价值 | 获客策略、定位差异化 | 留存策略、体验优化 |

**用法**：判断场景属于 Big Hire 还是 Little Hire，可帮助你校准四力量的赋值重心（Big Hire 看重 P/L，Little Hire 看重 A/I）。**仅用于校准赋值，不写入情境标签或任何输出列。**

### Demand Thinking（参考）

**核心原则**：从用户的挣扎（Struggle）出发设计产品，而非从功能出发。

| 传统思维 | Demand Thinking |
|---------|----------------|
| "我们要做什么功能" | "用户在挣扎什么" |
| "竞品有什么" | "用户在用什么自救" |
| "市场规模多大" | "有多少人在同一个挣扎中" |

**在场景库中的应用**：
- "用户具体场景"应描述挣扎（不是功能需求）
- "补偿行为"是 Demand 最强信号（用户已经在自费解决 = validated demand）
- "改进方向"应从挣扎出发（不是从竞品功能出发）

### 五种创新信号（参考，用于填写第二遍「创新信号类型」并校准「创新信号强度」取值）

下表的"类型标签"即为第二遍 ODI「创新信号类型」列的合法取值（外加"无"表示无信号）：

| 类型标签（填入列） | 定义 | 创新信号强度对应 |
|---------|------|----------------|
| 补偿行为 | 用户以非预期方式使用产品/组合工具/自创方案 | 4-5 |
| 非消费 | 用户本可以做但选择不做（如"太麻烦就不比价了"） | 3-4 |
| 不满意使用 | 用户在用但一直抱怨 | 2-3 |
| 异常使用 | 用户使用频率/方式与设计预期不符 | 3-4 |
| 情境变化 | 新情境出现使旧方案失效（如"有了孩子后出行完全不同"） | 3-5 |
| 无 | 无明显不满或补偿行为（强度=1 时填此） | 1 |

### 竞争三分类（参考，用于填写第二遍「竞争关系」列）

下表的"分类标签"即为第二遍 ODI「竞争关系」列的合法取值。判断依据是"当前主要方案"与"曾尝试或放弃的方案"两列描述的解决方案：

| 分类标签（填入列） | 定义 | 判断线索 |
|---------|------|---------|
| 直接 | 同品类替代方案（如携程 vs 飞猪，都是 OTA 订酒店） | 用户在同类产品/平台间比较或切换 |
| 间接 | 不同品类但解决同一 JTBD（如用小红书攻略+前台直订替代平台预订） | 用户用"非同类工具"达成同一进步 |
| 不用方案 | 用户放弃解决/自己硬扛/什么都不做（含补偿型自救） | 用户"宁可不做"或纯靠自创方案 |
| 无 | 原文未提及任何方案或竞争信息 | 该场景不涉及方案选择 |

## 五、第二轮 ODI 富化分析

### 5.1 定位与时机

第一轮（27列主表）完成后，**在同一次执行过程中**，对已生成的场景库进行第二轮分析，为每条场景补充 8 个源自 JTBD v3.0 四大学派的结构化字段（v3.2 在原 6 个基础上新增「创新信号类型」「竞争关系」两个清洁标签列，专为下游报告的聚合透视服务）。**第二轮的输入是已完成的27列表格（而非原始访谈文本），认知负荷更低、准确率更高。** 这是本 skill 在实战中反复验证的关键设计：先聚焦完成 JTBD 抽取，再在结构化结果上做 Ulwick 视角的富化，比"一遍同时做两套分析"质量显著更高。

最终交付物是一张 **35列** 的完整 Excel（27列主表 + 8列富化），由 AI 按序号自动合并，不需要用户手动合并。

### 5.2 富化表格式（独立 Markdown 表格，8列 + 序号）

输出一个独立的 Markdown 表格，用**序号**与主表一一对应：

| 序号 | Outcome Statement | Job Map阶段(Define\|Locate\|Prepare\|Confirm\|Execute\|Monitor\|Modify\|Conclude) | Job维度 | 创新信号强度 | 创新信号类型(补偿行为\|非消费\|不满意使用\|异常使用\|情境变化\|无) | 竞争关系(直接\|间接\|不用方案\|无) | 付费意愿信号(是\|否\|未提及) | 频次信号(日\|周\|月\|偶尔\|未提及) |
|------|-------------------|-------------|---------|-------------|-------------|-------------|-------------|----------|

### 5.3 字段定义

**· Outcome Statement（成果声明，必填，中文输出）：**
基于 Ulwick ODI 方法论，描述用户希望的可量化成果。**必须使用中文输出**（便于业务方直接阅读和引用到产品需求文档中，避免后续报告生成时再翻译导致信息损失）。
格式模板：`[减少/提升/消除/维持] [度量项] [对象]（[情境]）`
示例：
✓ `减少带娃家庭出行时验证酒店评价真实性的耗时`
✓ `提升多平台酒店比价时对价格公正性的信心`
✗ `让酒店预订更快`（太笼统，无度量项）
✗ `Minimize the time spent verifying hotel review authenticity`（禁止使用英文）
**动词对照表**（原 Ulwick 英文 → 中文）：Minimize→减少/降低，Increase→提升/增加，Maintain→维持，Eliminate→消除。
**OS 格式校验**：必须同时含动词(减少/降低/提升/增加/维持/消除) + 度量项 + 对象三要素，缺任何一项不合格。
**与"进步陈述"的区别**：进步陈述描述情感进步（Be目标），成果声明描述可量化的成果指标（Do目标）。两者互补，不可重复。

**· Job Map 阶段（必填，严格八选一）：**
Ulwick Universal Job Map 的8个阶段，从主表"进步阶段"4值映射到更细粒度：
- `Define` ← 明确需要什么（对应"想象"）
- `Locate` ← 寻找所需信息/资源（对应"搜索"）
- `Prepare` ← 准备执行方案（对应"搜索"后期）
- `Confirm` ← 确认决策正确性（对应"搜索"→"使用"过渡）
- `Execute` ← 执行方案（对应"使用"）
- `Monitor` ← 监控执行效果（对应"使用"中期）
- `Modify` ← 调整方案（对应"使用"中调整）
- `Conclude` ← 完成并评估（对应"实现"）

**· Job 维度（必填，七选一）：**
Wunker Jobs Atlas 的7个维度，标注该场景主要属于哪类 Job：
`Core Functional` | `Related` | `Emotional` | `Social` | `Financial` | `Consumption Chain` | `Context`
当多个维度都适用时，选**主要驱动力**对应的维度。

**· 创新信号强度（必填，纯整数1-5）：**
- 1 = 无信号（用户无明显不满或补偿行为）
- 2 = 弱信号（轻微不便但可忍受）
- 3 = 中等信号（有痛点但尚未自创方案）
- 4 = 强信号（已有补偿行为或明确的方案切换）
- 5 = 极强信号（用户投入大量成本自创解决方案，如截图比价3天）
（赋值时可参照第三章"五种创新信号"表做交叉校准。）

**· 创新信号类型（v3.2 新增，必填，六选一）：** `补偿行为` | `非消费` | `不满意使用` | `异常使用` | `情境变化` | `无`
标注该场景属于五种创新信号中的哪一类（取值与第三章"五种创新信号"表一致），供下游报告按类型聚合占比（如"非消费信号占比"）。判定要点：
- `补偿行为`：用户组合工具/自创方案/非预期使用（最强信号）
- `非消费`：用户本可做但选择不做（"太麻烦就不弄了"）
- `不满意使用`：在用但持续抱怨
- `异常使用`：使用频率/方式与设计预期不符
- `情境变化`：新情境使旧方案失效
- `无`：无明显创新信号
**与"创新信号强度"必须自洽**：强度=1 时类型填"无"；强度≥2 时类型不可填"无"。一般补偿行为↔强度4-5、情境变化↔3-5、非消费/异常使用↔3-4、不满意使用↔2-3。

**· 竞争关系（v3.2 新增，必填，四选一）：** `直接` | `间接` | `不用方案` | `无`
基于"当前主要方案"与"曾尝试或放弃的方案"两列，标注该场景反映的竞争关系类型（取值与第三章"竞争三分类"表一致），供下游报告做竞争格局透视。判定要点：
- `直接`：用户在同品类方案间比较/切换（如携程 vs 飞猪）
- `间接`：用户用不同品类工具达成同一 JTBD（如小红书攻略+前台直订）
- `不用方案`：用户放弃解决/纯靠自创方案硬扛
- `无`：原文未提及任何方案或竞争信息
**与"是否补偿行为"的关系**：补偿行为往往对应"不用方案"或"间接"竞争（用户绕过了标准方案），判断时可交叉印证。

**· 付费意愿信号（必填，三选一）：** `是` | `否` | `未提及`
用户是否直接或间接表达了"愿意花钱解决这个问题"。间接信号包括：已因此产生经济损失、对收费方案表示接受。

**· 频次信号（必填，五选一）：** `日` | `周` | `月` | `偶尔` | `未提及`
该场景在用户生活中的发生频率。旅行场景通常为"月"或"偶尔"；高频产品（如工具类App）可能为"日"或"周"。

## 六、质量自检与迭代优化（必须完整执行，不可跳过）

### 6.1 定位与执行时机

本章在第五章（ODI富化）完成后、第七章（validate.py格式校验）之前执行。目的是确保场景库在格式合规之前，先在**内容质量**层面达到最高标准。本章包含三个阶段共五轮检验，每轮必须输出小结，不可省略、不可合并、不可偷懒。

**执行顺序：** ODI富化完成 → 6.2三轮循环质量自检 → 6.3矛盾性检验 → 6.4系统性瑕疵检验 → 第七章validate.py格式校验

**硬性要求：** 三轮循环质量自检必须完整执行三轮，即使第一轮已无问题也必须执行第二轮和第三轮（作为交叉验证）。每轮都必须重新回到原始访谈文本中逐段比对，不可仅凭记忆判断。

### 6.2 三轮循环质量自检（必须完整执行三轮）

每轮自检从两个方向同时检查：

**方向一：去除（底料不足的场景坚决删除）**
- 该场景是否有充分的原文依据？如果"关键原话"字段找不到真实的用户原话支撑，说明底料不足
- 该场景是否在硬凑？判断标准：如果去掉这条场景，场景库的信息量是否有实质损失？如果没有，说明是凑数
- 该场景是否与其他场景高度重复？如果两条场景的核心信息相同只是换了说法，应合并或删除
- 该场景的进步陈述是否是从原文中真实提炼的？还是脱离原文的主观臆测？

**方向二：补充（遗漏的场景穷尽添加）**
- 重新逐段通读原始访谈文本，逐段检查是否有可独立成条的最小场景单元未被捕获
- 特别关注：补偿行为、情绪爆发点、方案切换时刻、用户主动提出的痛点——这些高价值信息最容易遗漏
- 检查访谈中被访者回答较短或较平淡的段落——这些往往被跳过，但可能包含有价值的信息
- 检查访谈末尾部分——通常信息密度较低但仍可能有遗漏的独立场景

**每轮输出格式（必须严格遵循，不可省略）：**

```
【第N轮质量自检小结】（N=1/2/3）

▶ 删除：X条
- 序号XX：删除原因（如"底料不足，原文中仅一句话带过且无具体行为细节"）
- 序号XX：删除原因

▶ 新增：X条
- 新增内容摘要 + 原文依据（引用具体原话）
- 新增内容摘要 + 原文依据

▶ 修改：X条
- 序号XX：修改内容（如"进步陈述从任务描述改为进步描述"）

▶ 本轮结论：当前场景库共X条，本轮净变化+/-X条
```

**三轮之间的递进关系：**
- 第一轮：粗筛，重点去除明显硬凑的、补充明显遗漏的
- 第二轮：精筛，重新通读原文，检查第一轮修改后是否引入新问题，以及是否有第一轮未发现的遗漏
- 第三轮：终审，以"如果这份场景库要交给业务方做产品决策"的标准做最后检查，确认每条场景都有实战价值

### 6.3 矛盾性检验（1轮，必须执行）

在三轮质量自检完成后，对场景库进行矛盾性专项检验。检查以下维度：

**检查维度：**

1. **同一用户态度矛盾**：同一用户在不同场景中对同一事物（如某平台、某功能、某类型酒店）的态度是否前后矛盾？如果矛盾，是否因为情境不同导致的合理差异（如商务出行vs亲子出行态度不同）？
2. **四力量与原话矛盾**：四力量评分（推力P/拉力L/焦虑A/惯性I）是否与"关键原话"字段中引用的原话逻辑一致？例如原话表达了强烈不满但推力P只给了2分，属于矛盾。
3. **进步陈述与场景矛盾**：进步陈述描述的进步方向是否与"用户具体场景"中描述的实际行为和情境匹配？
4. **情绪标注与上下文矛盾**：情绪状态的标签和强度是否与场景描述、原话内容逻辑一致？
5. **跨场景逻辑矛盾**：不同场景之间描述的时间线、因果关系是否自洽？

**输出格式：**

```
【矛盾性检验小结】

▶ 发现矛盾：X处
- 序号XX vs 序号XX：矛盾描述 → 修正方案
- 序号XX：内部矛盾描述 → 修正方案

▶ 合理差异确认：X处（看似矛盾但因情境不同属合理）
- 序号XX vs 序号XX：差异说明

▶ 本轮修改：X条场景受影响
```

### 6.4 系统性瑕疵检验（1轮，必须执行）

在矛盾性检验完成后，进行最后一轮沉浸式全量理解检验。要求：先将整个场景库从头到尾通读一遍，形成对该用户完整旅行决策逻辑的系统性理解，然后基于这个全局视角检查以下瑕疵：

**检查维度：**

1. **进步陈述质量**：每条进步陈述是否真的是"进步"（Be目标）而非"任务"（Do目标）？是否聚焦于用户想要成为什么状态，而非做什么事？
2. **情绪标注精准性**：情绪标签是否精准匹配场景中用户的实际情感状态？强度评分是否合理？
3. **行业术语精准性**：是否存在术语混用（如"挑房"vs"升房"、"改签"vs"退改"等）？
4. **主动需求vs被动验证**：标注是否准确？是否有被动验证的场景被错误标注为主动需求（导致推力P/拉力L虚高）？
5. **场景颗粒度**：是否有场景包含了两个以上独立诉求应拆分？是否有过度拆分的碎片应合并？
6. **Outcome Statement质量**：ODI富化中的Outcome Statement是否符合Ulwick标准格式？metric是否可量化？与主表进步陈述是否互补而非重复？
7. **整体叙事连贯性**：从全局视角看，这组场景是否完整还原了该用户的旅行决策逻辑？是否有断裂或跳跃？
8. **用户档案一致性**：同一用户的所有场景行中，用户档案（11项信息）是否完全一致？特别检查会员级别、消费力、年龄等关键标签是否存在前后不一致的情况——这类错误会直接导致后续报告中用户画像分析出错。
9. **关键原话归属准确性**：每条关键原话是否确实出自该用户？是否存在张冠李戴（把A用户的原话放到B用户的场景中）？特别注意同一项目中多位用户访谈并行处理时容易出现原话串行的问题。

**输出格式：**

```
【系统性瑕疵检验小结】

▶ 发现瑕疵：X处
- 序号XX：瑕疵类型 + 具体问题 → 修正内容
- 序号XX：瑕疵类型 + 具体问题 → 修正内容

▶ 质量确认：
- 进步陈述合格率：XX/XX条
- 情绪标注合格率：XX/XX条
- 行业术语零混淆：是/否
- 主动/被动标注准确率：XX/XX条

▶ 最终结论：场景库共X条，经五轮检验（3轮质量自检+1轮矛盾性+1轮系统性），质量达标/仍有X处需人工复核
```

### 6.5 执行纪律

**以下为硬性约束，违反任何一条等同于未执行本章：**

1. 三轮循环质量自检必须完整执行三轮，不可因"第一轮已无问题"而跳过后续轮次
2. 每轮必须重新回到原始访谈文本逐段比对，不可仅凭对场景库的记忆做判断
3. 每轮的小结必须完整输出，即使"删除0条、新增0条、修改0条"也必须明确写出
4. 矛盾性检验和系统性瑕疵检验不可合并执行，必须分步进行
5. 所有修改必须即时反映到场景库表格中，不可只在小结中描述而不实际修改
6. 如果五轮检验后仍发现问题，应继续修正直到问题清零，但不再要求额外输出小结
